# 事故响应 Runbook

最后更新：2026-06-18

本文档用于生产事故响应，覆盖密钥泄露、费用异常、飞书误停用、计费错误、队列失败、数据损坏等高风险场景。

## 1. 事故分级

| 等级 | 触发条件 | 响应要求 |
| --- | --- | --- |
| P0 | 大面积不可用、密钥泄露、费用持续异常增长、DB 损坏、误停用大量员工 | 立即止血，通知甲方负责人和运维负责人 |
| P1 | 部分员工不可用、单渠道故障、usage queue 持续增长、飞书通知大面积失败 | 1 小时内定位并给出恢复计划 |
| P2 | 单用户问题、单个通知失败、单个渠道余额显示异常 | 当日处理或纳入维护计划 |

## 2. 首 15 分钟流程

1. 明确事故类型和影响范围。
2. 指定事故负责人、执行人、记录人。
3. 保护现场：保存日志、截图、时间点、相关用户和渠道。
4. 先止血，后定位。
5. 禁止在未备份时执行数据恢复、计费重置、cleanup、seed。
6. 所有高风险操作必须双人确认。

## 3. 通用止血手段

按影响面从小到大选择：

- 禁用问题渠道。
- 将疑似员工个人额度设为 `0`。
- 删除或新建员工 Key。
- 关闭余额提醒：`BALANCE_ALERT_NOTIFY_ENABLED=false`。
- 关闭定时任务：`AUTO_SYNC_ENABLED=false`。
- 降低公开 API 流量或临时暂停 `/v1/*` 入口。
- 回滚代码 deployment。

## 4. INTERNAL_API_KEY 泄露

影响：

- 可调用 `/api/internal/*`。
- 若内部入口未被边缘层阻断，可调用 `/api/internal/admin/*` 自动任务接口：飞书同步、价格同步、余额同步、员工状态检查、排行榜发送等。

处理：

1. 立即轮换 `INTERNAL_API_KEY`。
2. 同步更新 Web 和 Proxy 环境。
3. 重新部署。
4. 检查事故窗口内内部接口日志。
5. 检查是否触发过计费重置、飞书同步、价格同步、余额同步。
6. 验证 `/api/internal/*` 公网仍为 404。
7. 验证 `/v1/models` 和一次 chat 调用。

## 5. 供应商 Key 泄露

处理：

1. 在供应商控制台停用或删除泄露 Key。
2. 在 Sparkloom 渠道管理中重新录入新 Key。
3. 手动同步余额。
4. 检查供应商账单和事故窗口调用。
5. 如无法确认费用，临时禁用该渠道。
6. 写入事故记录。

## 6. 员工 Key 泄露

处理：

1. 定位用户。
2. 删除泄露 Key。
3. 要求用户新建 Key。
4. 检查该用户事故窗口 usage。
5. 必要时将个人额度临时设为 `0`。
6. 如影响供应商账单，进入资金核账流程。

## 7. 费用异常暴涨

处理：

1. 按小时导出事故窗口 usage。
2. 按用户、渠道、模型聚合。
3. 查是否有单用户或单模型突增。
4. 检查模型价格是否被误改。
5. 检查汇率来源是否为 `hardcoded` 或异常值。
6. 检查是否存在 queue 重放或重复入账。
7. 临时设置相关用户额度为 `0` 或禁用问题渠道。
8. 对照供应商后台账单和余额变化。

## 8. 飞书误停用大量员工

处理：

1. 立即设置 `FEISHU_MAX_AUTO_DISABLE_DEPARTED=0`。
2. 检查飞书应用可用范围。
3. 检查通讯录数据范围。
4. 检查通讯录权限。
5. 手动同步前先备份 DB。
6. 修复范围后手动同步。
7. 抽查恢复员工。

## 9. usage queue 持续失败

检查：

```bash
wc -l /data/usage-queue.jsonl
wc -l /data/usage-dead-letter.jsonl
tail -n 20 /data/usage-dead-letter.jsonl
```

判定：

- pending 持续增长：优先查 Web `/api/internal/usage`、`INTERNAL_API_KEY`、Web health。
- dead-letter 新增：通常是模型价格缺失、用户/渠道不存在、usage 数据被 Web 拒绝。
- dead-letter 不是送达队列，不能直接追加回 queue。

止血：

- 不要删除 queue 文件，除非已确认对应 usage 不再需要入账并完成备份。
- 高风险时禁用问题渠道或临时降低流量。
- 修复原因后观察 pending 是否下降。

## 10. 数据回滚

数据回滚只在确认数据损坏时执行。

原则：

- 先停止写流量。
- 成套恢复 `data.db`、`usage-queue.jsonl`、`usage-dead-letter.jsonl`。
- 不要混用不同时间点的 DB 和 queue。
- 恢复前备份当前现场文件。
- 恢复后做小流量验证。

## 11. 代码和环境回滚

回滚分三类，不能混用：

1. 代码回滚：优先在 Railway 控制台 redeploy 上一个成功 deployment；如需 Git 回滚，使用 revert commit 后重新部署。
2. 环境变量回滚：只回滚本次变更变量，必须对照发布前变量快照。
3. 数据回滚：按上一节处理。

不得随意回滚或轮换：

- `ENCRYPTION_KEY`
- `INTERNAL_API_KEY`
- `JWT_SECRET`

回滚后验证：

- `https://ai.seapllo.com/health`
- 内部 `/api/health`
- 管理员飞书登录
- `/v1/models`
- 一次小流量 chat 调用并确认 usage 入库
- Railway 日志 10 分钟内无 `[railway] exited`、`[Usage] Flush error`、`[FeishuBot] Failed`

## 12. 复盘记录模板

每次 P0/P1 必须记录：

- 事故编号。
- 发生时间和恢复时间。
- 影响用户、渠道、模型、费用。
- 根因。
- 止血动作。
- 数据恢复动作。
- 密钥轮换动作。
- 验证结果。
- 责任人。
- 后续修复项。
