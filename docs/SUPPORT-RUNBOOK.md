# 业务支持 Runbook

最后更新：2026-06-18

本文档面向一线管理员、客服和业务支持人员，用于处理员工使用、飞书授权、API Key、排行榜、余额提醒、部门归属等日常问题。

## 1. 支持原则

- 不向员工索要完整 API Key。
- 不在工单、截图、聊天中保存完整密钥。
- 不直接删除真实员工。
- 不直接改生产数据库。
- 不绕过审批修改渠道 Key、价格、额度、权限。
- 遇到资金、权限、密钥、批量停用问题，按 `INCIDENT-RUNBOOK.md` 升级。

## 2. 员工入职开通

1. 确认员工已在飞书通讯录中。
2. 确认 Sparkloom 飞书应用可用范围包含该员工。
3. 等待定时同步，或由管理员手动触发飞书通讯录同步。
4. 确认员工状态为 `active`。
5. 确认员工部门、中心、组归属正确。
6. 员工首次登录 `https://ai.seapllo.com`。
7. 员工进入 `/dashboard/key` 新建自己的 `sk-emp-...` Key。
8. 告知员工完整 Key 只显示一次，丢失后只能新建。

验收：

- 员工能登录。
- 员工能看到个人用量页。
- 员工能新建 Key。
- 用完整 Key 调 `/v1/models` 成功。

## 3. 离职和误停用

系统会通过飞书同步和员工状态检查识别离职或离开应用范围的员工。

正常离职：

- 用户状态变为 `disabled`。
- 旧 session 下次刷新失效。
- 员工 API Key 不能继续调用。
- 历史用量保留，用于分账和审计。

误停用处理：

1. 检查飞书应用可用范围是否被缩小。
2. 检查通讯录数据范围是否被缩小。
3. 检查飞书通讯录权限是否被取消。
4. 修复飞书范围或权限。
5. 手动触发飞书同步。
6. 如果仍未恢复，管理员可临时恢复用户为 `active`。
7. 记录误停用原因和恢复时间。

大量误停用时：

- 立即通知运维和值班负责人。
- 临时设置 `FEISHU_MAX_AUTO_DISABLE_DEPARTED=0`，避免继续自动停用。
- 不要批量删除用户。

## 4. 部门映射口径

部门归属用于：

- 部门额度。
- 部门排行。
- 部门分账。
- 部门负责人可见范围。
- 排行榜部门统计。

当前部门映射在代码中维护：

- `web/src/app/api/setup/sync-feishu/constants.ts`

映射类型：

- 组名归属部门。
- 不规则部门名重命名。
- 部门中心兜底。
- 个别用户强制覆盖。
- 硬编码管理员保护。

变更流程：

1. 业务确认标准部门口径。
2. 技术修改映射常量。
3. 在测试库或备份库同步验证。
4. 验证员工详情、部门排行、部门分账、部门负责人视图。
5. 生产发布后手动同步一次飞书。
6. 抽查异常人员。

发现“未知/未分配”人员时：

- 先核对飞书组织架构。
- 再判断是否需要新增映射规则。
- 不要直接在 DB 临时改部门作为长期方案。

## 5. 飞书授权范围检查

飞书有三类范围，问题表现不同：

| 范围 | 决定什么 | 异常表现 |
| --- | --- | --- |
| 应用可用范围 | 员工能否登录 Sparkloom | 授权按钮灰色、提示无权限 |
| 通讯录数据范围 | 系统能否同步员工和部门 | 员工缺失、大量离职候选、部门异常 |
| 机器人群范围 | 群通知和排行榜 | 群列表为空、排行榜发送失败 |

OAuth 回调必须包含：

```text
https://ai.seapllo.com/api/auth/feishu/callback
```

飞书权限或范围变更后，需要重新验证：

- 管理员登录。
- 普通员工登录。
- 通讯录同步。
- 私聊测试通知。
- 群列表刷新。
- 排行榜测试发送。

## 6. 排行榜业务口径

排行榜统计：

- 北京时间当月。
- 只统计 `active` 员工。
- 只统计本月费用大于 0 的用户。
- 个人榜按费用降序取 TOP 10。
- 部门榜按费用降序取 TOP 5。
- 内容包含费用、调用次数、活跃用户数和部门汇总。

发送前检查：

1. 排行榜总开关已启用。
2. 发送频率已设置。
3. 目标群组已保存。
4. 机器人仍在目标群内。
5. 飞书应用具备读取群和发送消息权限。
6. 本月有 usage 数据，或测试发送允许空数据。

## 7. 余额提醒处置

余额同步默认每小时执行。

余额提醒默认北京时间：

- 09:30
- 12:00
- 14:30
- 17:30

等级：

- `warning`：余额低于阈值。
- `danger`：余额低于阈值的 20%。

收到告警后：

1. 确认渠道是否 `active`。
2. 确认余额是否为最新同步值。
3. 确认是否只是历史告警记录。
4. 联系渠道充值负责人。
5. 无法及时充值时，临时禁用渠道或调整主备渠道。
6. 充值后手动同步余额。

说明口径：

- 禁用渠道不会继续触发新的余额告警。
- 历史告警记录不会自动删除。
- 余额同步成功不等于飞书消息一定送达。

## 8. API Key 支持边界

客服不得要求用户发送完整 Key。

可要求用户确认：

- 是否以 `sk-emp-` 开头。
- 是否复制自“新建成功”的一次性明文。
- 是否包含星号。
- Key 末四位。

处理 401：

1. 让用户新建 Key。
2. 立即复制完整明文。
3. 确认客户端填写的是 `sk-emp-...`。
4. 确认不是 DeepSeek、硅基流动、OpenAI、Anthropic 官方 Key。
5. 验证 `/v1/models`。

验证命令：

```bash
curl https://ai.seapllo.com/v1/models -H "Authorization: Bearer sk-emp-完整key"
```

## 9. Claude Code 配置

Claude Code 使用：

```text
Base URL: https://ai.seapllo.com/anthropic
API Key: 员工自己的 sk-emp-...
```

如果使用环境变量：

```bash
ANTHROPIC_BASE_URL=https://ai.seapllo.com/anthropic
ANTHROPIC_API_KEY=sk-emp-完整key
```

常见错误：

- 填成 `https://ai.seapllo.com/v1`：Claude Code Anthropic 模式会失败。
- 填了供应商官方 Key：返回 401。
- 填了带星号脱敏 Key：返回 401。
- 模型名不存在或缺价：返回无渠道或缺价错误。

## 10. 常见回复话术

登录失败：

```text
请先确认你使用的是公司飞书账号。我会检查你是否在 Sparkloom 应用可用范围内，以及账号是否被系统标记为 disabled。
```

Key 无效：

```text
请确认客户端里填写的是完整 sk-emp-...，不是带星号的脱敏 Key，也不是供应商官方 Key。完整 Key 只在新建时显示一次，丢失后请新建。
```

429 超额：

```text
429 可能来自个人、部门或公司任一层额度，也可能是大请求的额度预占。我们会核对本月用量、额度规则和是否存在未释放预占。
```

排行榜未发送：

```text
请确认排行榜已启用、已选择群组、机器人在群内，并且飞书应用具备读取群和发送消息权限。
```

余额告警：

```text
告警表示某个启用渠道余额低于阈值。我们会先复核渠道状态和最新余额；如果是历史告警，当前状态不会受影响。
```

## 11. 升级标准

必须升级给技术或运维：

- 多人同时无法登录。
- 大量员工被标记离职或 disabled。
- 费用异常暴涨。
- 供应商 Key 疑似泄露。
- 员工 Key 疑似泄露且无法定位。
- usage 不入账或 queue 堆积。
- 飞书通知大面积失败。
- 渠道余额为负或与供应商控制台明显不一致。
- 任何需要 DB 恢复、计费重置、cleanup、seed、密钥轮换的操作。
